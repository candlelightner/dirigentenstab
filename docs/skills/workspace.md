Name: workspace

Description: Create a ready workspace VM for an AI harness (Claude Code, Codex, Gemini CLI, opencode or another) with the hub MCP export configured and logins, files and chat histories kept on a persistent volume, reachable over SSH and/or a noVNC desktop.

Text:

Use this when the owner asks for a workspace, or a place to run an AI harness against this hub. Workspaces are ordinary CloudStack VMs. Ask the owner only what is genuinely missing: which harness or harnesses (any, not only the ones named here), and the console, SSH and/or a graphical noVNC desktop. Do not assume either.

1. Capacity: `execute_api('listCapacity')`. Do not deploy if the target cluster would pass CloudStack's 85% allocation threshold; report the shortfall. Choose the smallest compute offering that fits: harness CLIs need about 2 GB RAM (2 vCPU / 4 GB is comfortable), a graphical desktop more (about 4 GB), with a root disk of at least 20 GB.
2. Template: prefer the owner's `dev-vm` template: `execute_api('listTemplates', templatefilter='executable', name='dev-vm')` (`self` hides a template shared by another domain, issue #100). Otherwise use an Ubuntu 24.04 cloud-init template and install each requested harness with its official installer. For a desktop, follow docs/DESKTOP_TEMPLATE.md (or use a desktop template if one exists), including its console video settings. Never build or modify templates unprompted.
3. Deploy with `execute_api('deployVirtualMachine', ..., managed=true)`, a descriptive `name` and `displayname` such as `ws-<harness>-<purpose>`, and never custom `userdata`. Tag it so the sidebar lists it under Workspaces: `execute_api('createTags', resourceids=<vm id>, resourcetype='UserVm', tags[0].key='dirigentenstab-workspace', tags[0].value=<harness>)`. Then `run_vm_command(vm_id, 'cloud-init status --wait')`. Managed access creates the guest user `dirigent` (sudo, key-only login) and installs the owner's SSH public key for it; everything below runs as `dirigent` and uses `/home/dirigent`.
4. Missing harnesses: install only what the owner asked for, via the vendor's official installer or package (for example `npm install -g` into `/usr/local` with `sudo`). Verify with `<harness> --version`.
5. Persistence. Keep one persistent data volume per owner, named `workspace-home`. Look it up first (`listVolumes name=workspace-home`); only if absent create it once (`createVolume` with a small data disk offering, for example 20 GB). Attach it to the active workspace (`attachVolume`). In the guest:
   - Find the device (`lsblk`) and run `sudo blkid <device>`. Format (`sudo mkfs.ext4 -L workspace-home <device>`) only if blkid prints nothing. Never format a volume that has a filesystem.
   - Mount it at `/mnt/workspace-home` through an `/etc/fstab` line using `LABEL=workspace-home` and `defaults,nofail`, then `sudo mount -a`.
   - Bind-mount the owner's state onto it so logins and native chat histories survive stop/start and workspace replacement. For each of `.claude`, `.claude.json`, `.codex`, `.gemini`, `.local/share/opencode`, `.config/gh` and `work` (plus the state directory of any other installed harness): create the target under `/mnt/workspace-home/` if missing (a directory, or an empty file for `.claude.json`), create the matching path under `/home/dirigent`, `chown` both to `dirigent`, add a `bind` line with `nofail` to `/etc/fstab`, and mount it. If a state path already holds data in the guest and the volume copy does not exist, move it onto the volume with `mv` before mounting; never overwrite existing data on the volume.
   - Replacing a workspace: stop the old one, `detachVolume`, attach to the new one and repeat only the mount steps above. One VM uses the volume at a time. If the owner wants several concurrent workspaces on shared files, offer CloudStack Shared FileSystem (`createSharedFileSystem`) instead.
   - Never delete the home volume unless the owner explicitly asks.
6. Hub MCP export, so the harness uses this agent's tools. Use the placeholders `{{mcp_url}}` and `{{mcp_key}}`; the hub fills them in at execution time. Never ask for, print, store or write the token anywhere else. Pass them through `env` or put them in `write_vm_secret_file` content only.
   - Claude Code: `run_vm_command(vm_id, 'claude mcp add --scope user --transport http dirigentenstab "$MCP_URL" --header "Authorization: Bearer $MCP_KEY"', env={'MCP_URL': '{{mcp_url}}', 'MCP_KEY': '{{mcp_key}}'})`.
   - Codex, Gemini CLI, opencode (file configs): if the config file exists, read it first (never credential files such as `auth.json`) and merge the entry instead of overwriting; write the result with `write_vm_secret_file` (the placeholders appear in the content). Codex `~/.codex/config.toml`: table `[mcp_servers.dirigentenstab]` with `url = "{{mcp_url}}"` and `http_headers = { Authorization = "Bearer {{mcp_key}}" }`. Gemini `~/.gemini/settings.json`: `mcpServers.dirigentenstab` with `httpUrl` and `headers.Authorization`. opencode `~/.config/opencode/opencode.json`: `mcp.dirigentenstab` with `type: "remote"`, `url` and `headers.Authorization`. Keep these files owned by `dirigent` and persisted if their directories are on the volume; add `.config/opencode` to the bind list if needed.
   - Other harnesses: use their documented remote (Streamable HTTP) MCP configuration the same way.
   - Verify reachability: `run_vm_command(vm_id, 'curl -s -o /dev/null -w "%{http_code}" "$MCP_URL"', env={'MCP_URL': '{{mcp_url}}'})`. Without the token, 401, 405 or 406 means the hub is reachable. If the name does not resolve or the connection fails, tell the owner; do not guess addresses.
   - The key is per VM and the owner can revoke it in this agent's Configure, MCP export.
7. Console:
   - SSH: give the owner the VM name, its address and the user `dirigent`. The hub's embedded terminal in the VM view works, as does the owner's own SSH client (their public key is already installed).
   - Graphical: install a light desktop as in docs/DESKTOP_TEMPLATE.md, then point the owner to CloudStack's noVNC console in the hub's VM view. The graphical login password is set by the owner at the console (`sudo passwd dirigent` is theirs to run); never create, store or send it.
   - Other consoles (browser terminal, code-server, `code tunnel`) only if the owner asks.
8. Logins: the owner runs the one-time logins over SSH or the console: `claude` then `/login`; `codex login --device-auth`; `gemini` then `/auth`; `opencode auth login`; `gh auth login`; `code tunnel`. Never run them yourself. Never read, print, copy or transfer credential files in the guest (for example `~/.claude*`, `~/.codex/auth.json`, `~/.gemini`, `~/.local/share/opencode/auth.json`, `~/.config/gh`). For token tools such as `gh`, if a granted secret name is listed in `secret_names`, use `{{secret:NAME}}` in `env` or `write_vm_secret_file` instead of asking for the token. Do not enable bypass or auto-approve permission modes; the owner decides.
9. Lifecycle: stop a workspace (`stopVirtualMachine`) when the owner says so; state stays on the volume and a later `startVirtualMachine` resumes it (re-check that the mounts came up). Destroy only workspaces you created, or a descendant's when the owner asks, and only on request: stop it, unmount, `detachVolume` the home volume first, then `destroyVirtualMachine` without expunging the volume. To list workspaces, including descendants' that your own identity may administer: `listVirtualMachines listall=true tags[0].key=dirigentenstab-workspace`.

# Security

Dirigentenstab is an administrative application. An authorized agent can change and destroy CloudStack resources inside its delegated domain. Keep management and guest networks private and use CloudStack quotas, backups and domain boundaries.

## Credentials and sessions

All CloudStack keys, provider keys, MCP bearer credentials, guest private keys, the owner's optional terminal SSH private key and passphrase, CloudStack browser sessions, and conversation messages use Fernet authenticated encryption. The master key is a separate file mounted as a Docker secret. SQLite UUIDs, display names, provider and MCP URLs, tool assignments, conversation titles and audit metadata remain plaintext. Back up the master key independently; losing it makes encrypted records unrecoverable.

The application never stores a human CloudStack password. Login attempts are bounded by persistent per-client and per-username limits. Session cookies are opaque, HttpOnly, Secure and SameSite Strict; only hashes are indexed in SQLite. Logout revokes the local session even if CloudStack is temporarily unavailable. CloudStack user/account status is checked again on protected operations. There is no public registration.

HTTP mutations and socket handshakes require the configured exact HTTPS Origin. Logout also requires the session CSRF token. Socket events are bound to the session that created the NiceGUI client and to its registered socket. Reverse proxies must preserve Origin, cookies and WebSocket upgrades; do not add wildcard CORS or trust arbitrary forwarded client headers.

CloudStack console tickets are requested through the signed-in human’s native permissions. The console proxy binds short-lived grants to that browser session and validates the session on HTTP and WebSocket access; it accepts no browser-supplied upstream URL or transport target. Native noVNC assets and WebSocket traffic travel over the application’s HTTPS/WSS origin, with private HTTP/WS access to the trusted CPVM behind it. Only `/vm-console/` responses allow same-origin framing; other application responses retain `X-Frame-Options: DENY`. Native console assets are trusted code served on the application origin.

## Infrastructure keys

Each managed agent account has one encrypted CloudStack API key pair, shared by generic API calls and managed subgroup provisioning. CloudStack's current account, domain and role authorize every infrastructure request. New keys contain no additional per-key allow/deny rules; the application adds no command blacklist, parameter-name blacklist or duplicate infrastructure permission table. Search and description use the same identity's live `listApis` catalogue, including service-offering, account and domain APIs that CloudStack permits.

Native API denials are returned under that same identity. The backend never substitutes a parent, bootstrap or host-controller key to make an agent request succeed. Local transport validation prevents command injection, CloudMonkey `@file` expansion and credential/configuration selectors; these checks protect the application process and do not grant or remove CloudStack APIs. Secrets returned by native APIs are redacted before model history or UI display. Keep each managed account's role and domain appropriate for the resources it should control.

The managed subordinate-agent feature switch controls creating an application AI-agent entity, its model/instructions and durable provisioning workflow. It does not authorize or deny ordinary CloudStack APIs: native-authorized `createDomain`/`createAccount` remain usable through the runtime tools regardless of that feature switch. Conversation ownership, managed guest SSH enrollment and privileged host-helper policies remain application/host security boundaries.

Rotation and explicit adoption verify the exact native agent user/account/domain and keep recovery state until the replacement is validated and committed. No key is silently selected or replaced by a privileged identity after failure. Schema migration retains existing active credentials and stores the retired provisioning pair encrypted for deliberate cleanup; it does not delete or revoke remote keys. Existing native key restrictions remain effective until an administrator explicitly replaces that legacy key with the account's normal API key pair.

CloudStack permissions and quotas are the final infrastructure boundary. The installer must not expose unauthenticated libvirt TCP, disable host SSH protections, or attach existing host directories to guest VMs. Dedicated NFS secondary storage is owned and controlled by platform setup; it is not a general host export or an agent-selectable mount.

The isolated Basic-zone guest subnet uses the host as its gateway and a scoped masquerade rule. Its persistent forwarding helper adapts CloudStack's bridge-only structural checks to routed guest packets while keeping live native VM IP sets and security-group egress chains authoritative. A source-IP guard runs before DHCP exceptions, unknown native ports drop, and uplink replies require established/related connection state. The helper edits only its own chain and tagged jumps, without flushing shared tables or opening new inbound guest access. Removed VM mappings disappear on the next timer pass; native teardown flushes any temporarily referenced empty chains/IP sets, so stale references fail closed.

The application does not create or attach network security groups during managed VM deployment. Explicit security-group IDs/names are forwarded unchanged; CloudStack and the requesting identity own network policy. Existing native rules are not automatically deleted. This does not change per-VM SSH credentials, host-key verification or ownership checks.

The optional Tailscale forwarding helper grants authorized tailnet clients host-routed access to all ports on the private IPv4 VM subnet, including system VMs. This administrator ingress path is separate from native VM-to-VM and egress isolation, which remain enforced on the host. The helper only accepts requests arriving on `tailscale0` and established/related replies, retaining Tailscale SNAT and the existing LAN/internet ingress blocks. Tailnet policy controls client identity authorization; it must grant only the intended users/devices access to the subnet. See [private Tailscale VM access](CONSOLE_ACCESS.md).

## Models and data

The configured provider receives the prompt, compact domain context and requested tool results. Choose local inference when these must remain on your machine. Provider configuration is platform-admin only. Keys are decrypted only inside the backend and are redacted from tool responses and stored histories. Treat tool results and model instructions as untrusted; authorization does not depend on prompts.

Managed template cloud-init includes a generated *guest host* private key, allowing a public key to be pinned before SSH. This key is unique to the guest and has no host privileges. User-data is encrypted locally and redacted from generic API responses. Models never receive guest client private keys, CloudStack keys or provider keys. Existing VMs without enrolled SSH credentials or host-key pins fail with a missing-access error.

Managed cloud-init disables password and root SSH and adds no sudo by default. Enrollment does not remove privileges or secrets already baked into an image; prepare and sanitize custom templates before reuse. File transfers expose only that agent's application workspace; local path arguments are basenames, with an 8 MiB file limit. The application has no Docker socket, hypervisor socket, SSH agent or arbitrary host directory mount.

## External MCP tools

MCP is optional and uses Pydantic AI's existing remote Streamable HTTP support. Only HTTPS endpoints without embedded credentials, query strings or fragments are accepted; local stdio/process transports are unavailable. Endpoint and bearer-credential administration requires a human CloudStack administrator authorized for the main agent's domain. Child administrators cannot replace an inherited endpoint or secret; they may assign only tools allowed by every ancestor agent. This application tool assignment does not grant CloudStack infrastructure permissions.

Automatic tool discovery lists available tools without granting access. Only explicitly checked and saved tools are assigned; a discovery failure does not remove saved assignments. Assignments default to empty, including newly created agents. The backend verifies live CloudStack ancestry and intersects explicit tool names across the full agent chain. Authorization, current endpoint configuration and effective assignments are checked again before dispatch, so an ancestor revocation or server disable applies to subsequent calls. Missing ancestry fails closed. Agent tools cannot register servers, change assignments or retrieve credentials. Credentials stay encrypted at rest and are decrypted only for backend HTTP authentication; echoed credentials are redacted from results and saved histories.

MCP server instructions, model sampling and elicitation are disabled. Tool descriptions and results remain untrusted external data, never an authorization source. A custom per-agent system prompt cannot override backend permission checks. Configured servers receive tool arguments, which may contain private data: review the selected service and its tools before granting access.

Generic external tools may have side effects even when their metadata claims otherwise. Every MCP call therefore uses durable mutation tracking and its tool-call identity. Completed results are reused; ambiguous failures are not automatically replayed and require administrator review. Disabling an endpoint prevents new calls but cannot undo a request already accepted remotely.

## Operations

Keep `.env`, `secrets/`, databases and host setup state outside Git. Host setup logs and bootstrap identities are root-private. Never paste them into issues or model chats. Debug logging in CloudStack can contain sensitive API information; use INFO logging and revoke keys if diagnostic output exposes them.

Public GH Actions execute fixture-based tests only. Real infrastructure tests require explicit invocation on a trusted private environment. Do not run untrusted pull-request code on your administrative host. Images are published by version tags; deployment is a separate administrator action.

Private build capabilities are explicit: the backend adds guest-local sudo only for an approved build template, while non-root SSH, per-VM keys and host-key pins remain mandatory. The explicit `managed=true` private-template workflow accepts owned stopped managed root volumes and private images. Default native `createTemplate` and `deployVirtualMachine` calls retain every native-authorized parameter, including publication settings, owner selectors and custom user-data; they do not receive automatic managed SSH enrollment or template approval. Uncertain image creation requires reconciliation before repetition. Operator-approved assets are separately bound to exact agent IDs and verified by size/SHA-256 before SFTP; arbitrary workspace transfers keep their 8 MiB bound. The existing application volume holds these read-only binaries; no additional host mount is introduced. Dashboard quicklinks are human platform-admin only, contain no credentials and use a separately configured browser endpoint.

Managed GPU lifecycle requests use the existing private controller only for a current authenticated human's own durable agent execution. Reconfiguration requires every ancestor's explicit permission and proof that affected devices are unused and owned within the permitted domain scope. Agents cannot change these host-controller policy or ownership grants. Native VM requests retain the selected agent's CloudStack identity; an API denial never triggers a privileged native retry.

# Dirigentenstab 0.1.4 — bounded task continuation

Execution `1511d6c3-221b-4c96-8b76-b689133e5c74` exhausted the **30-tool-call limit** after 13 model responses and 97.7 seconds. It reached neither the 20-request nor the 360-second limit. One `deployVirtualMachine` tool call was rejected by local validation because `networkids` was a JSON array; CloudMonkey requires a comma-separated string. No deployment ledger entry or VM was created by that request. Its 31st proposed call was not executed.

Each execution window retains limits of 20 model requests and 30 tools. Up to three windows continue automatically from persisted messages, including pending calls that Pydantic AI has not executed. Windows also yield at safe model/tool boundaries after 900 seconds. Each invocation has a hard 1,800-second ceiling and reserves 720 seconds before starting another infrastructure operation, matching existing bounded CloudStack/SSH waits. Provider requests have a 60-second timeout. Exhausting the invocation allowance pauses explicitly; **Continue saved task** reopens the same operation and human-owned conversation without inventing another user task or forgetting results. The UI displays requests, tools, windows, reused results and the pause reason. Imported histories and stale checkpoints cannot be resumed as mutable tasks.

Migration 008 adds one encrypted checkpoint column. Creation intents are deduplicated by agent/tool/arguments; other mutations retain their tool-call identity so a resumed pending call cannot silently execute twice, while a genuinely new verification command can observe fresh state. Unknown dispatches block further mutation and require reconciliation. Budget pauses and provider interruptions preserve messages, completed results, pending plans and operation identifiers. Restart can reopen a checkpoint only when no mutation was interrupted during dispatch.

Discovery shares one concurrent CloudStack catalogue fetch. Search/description results are reused for 300 seconds; identical read-only inventory queries for 10 seconds. Successful mutations invalidate inventory caches. Authorization is checked before cache hits. Available API names, scalar parameter formatting, backend-managed SSH and the native compatible offering are explained to the model. Credentials, domain rights, quotas, pinned host keys and non-root guest identities retain their existing enforcement.

For a failed deployment, first use `scripts/admin.py status` and the existing `recover-deployments` or confirmed-rejection workflow. Then authenticate its human owner through `scripts/admin.py repair-execution RUN_ID --deployment-id DEPLOYMENT_ID`. It verifies the saved arguments and deployment ownership, accepts only resolved ledger states, preserves recovered VM results or records an explicitly rejected attempt, and cancels stale unexecuted plans. It does not create another VM. Unrelated or ambiguous actions remain blocked.

## Native application SSH path

The live VM test identified a separate prerequisite: CloudStack's bridge forwarding rules drop routed Docker traffic, although host-originated SSH reaches the guest. The native helper allows only `172.30.253.2/32` through the application's Docker bridge to `10.253.80.0/24` through `dscloud0` on TCP/22, plus established replies. It does not open host SSH, change default policies, flush CloudStack rules or permit guest-initiated connections to the application. Domain authorization, per-VM keys and host-key pins remain mandatory.

Fresh native installation includes the helper automatically, without importing any existing resources. For an existing native installation, obtain operator authorization and apply only its narrow installer with `sudo .venv/bin/python scripts/native_setup.py --guest-ssh`; do not rerun the native installer on an existing host. A small oneshot/timer maintains the two tagged rules because CloudStack can recreate its bridge drops. Roll back by disabling `dirigentenstab-guest-ssh.timer` and running the installed helper with `--remove`; it removes only its own tagged rules. Existing host rules/services are retained.

The opt-in `scripts/live_lifecycle_acceptance.py --run` exercises the real authenticated web interface, configured provider, managed VM provisioning, guest Python/SSH, stop and reload. A private receipt supports `--resume` without resubmitting the task. Optional cleanup uses the operator's existing privileged key only for the verified disposable VM; expunge permissions are never added to agent keys. No production credentials are put into CI fixtures.

CI includes a three-turn conversation around a 65-tool lifecycle chain using the production request/tool limits, automatic windows, restart and manual continuation. It verifies retained earlier answers/results, one creation dispatch despite a repeated creation intent, stable operation ownership and no synthetic user prompts. Browser CI also sends a second turn after budget continuation and verifies both turns after reload. These tests use synthetic provider and CloudStack responses; the opt-in live acceptance uses the configured real provider.

Local validation: 220 unit/integration tests, plus five Chromium/Firefox browser scenarios. Physical Android keyboard behavior and a destructive fresh bare-host reinstall were not exercised on the production server. The fresh-install path and scoped upgrade path share the same tested installer function; no imported-resource files are required.
